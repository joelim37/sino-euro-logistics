# 网站项目复盘与复用手册（基于 Sino Euro Logistics 项目）

> 目标：把这个网站从立项到当前版本的关键经验、架构方法、执行步骤、踩坑记录、上线注意事项整理成一份可复用文档，供后续新网站项目直接参考。

---

## 1. 项目定位与整体思路

这个项目不是单纯做一个“展示型官网”，而是逐步演进成：

1. **可后台维护的企业官网**
2. **可持续扩内容的 SEO/GEO 站点**
3. **可承接询盘和转化的销售型网站**
4. **可复制到其他行业/客户的新站模板**

所以后续新网站不要只盯着“页面做出来”，而要一开始就按下面 4 层设计：

- **前台展示层**：首页、服务页、关于页、联系页、新闻页、专题页
- **后台运营层**：内容编辑、媒体库、服务管理、询盘管理、配置管理
- **数据层**：Supabase 表、Storage、site_config、模块配置
- **增长层**：SEO、结构化数据、内容扩展、转化路径、反垃圾询盘

**结论：新网站应该从 Day 1 就按“可运营的网站系统”来做，而不是做成静态页面后再补。**

## 2. 项目演进脉络

### 阶段 A：最初版本（展示站雏形）
最初做的是一个专业物流官网，包含：

- 首页
- 服务展示
- 路线/产品展示
- 基础后台
- 简单中英文切换

早期技术上经历过：

- React + Vite + Tailwind 版本
- 需要 `vercel.json` 支持 SPA 路由
- index.html 层面的基础 SEO/Favicon 修正
- 早期后台是前端本地保护逻辑

### 阶段 B：接入 Supabase，变成可运营 CMS
后面核心变化是：

- 菜单、服务、模块配置接入 Supabase
- 新增 `site_modules` 存储首页模块数据
- 后台从“写死页面”转向“可视化编辑内容”
- 支持中英文内容分离/切换

这个阶段最大的价值是：

- 内容修改不再依赖开发改代码
- 网站开始具备复制能力
- 后续每个模块都可抽象成 CMS 配置项

### 阶段 C：切到 Next.js + App Router + 生产级部署
后期正式生产版本落在：

- **Next.js 14 App Router**
- **Vercel 生产部署**
- **Supabase 数据与存储**

生产项目确认是：

- **Vercel project**: `sinoeurologistics-atpr`
- **workspace folder**: `sino-euro-logistics-gh`

这里有一个非常重要的历史教训：

> 工作区里存在另一个相似目录 `new_site/sino-euro-logistics`，但它绑定的是不同 Vercel 项目，曾导致“本地改了但线上不是这个站”的混乱。

**复用建议：每个新网站开始前，第一件事先确认 3 个映射：**

- 本地目录是哪一个
- GitHub 仓库是哪一个
- Vercel 项目是哪一个

否则非常容易改错项目。

## 5. 数据结构设计经验

这个项目里，最值得后续复用的不是具体表名，而是思路。

### 5.1 `site_config`
适合放：

- 公司名 / 电话 / 邮箱 / 微信 / 地址
- 首页 banner 文案
- footer 文案
- 首页新闻数量
- 询盘通知邮箱
- 顶部推荐文章 ID
- 各种全局开关 / 默认值

**原则：凡是全站范围的轻配置，尽量进 `site_config`。**

### 5.2 `services`
适合放：

- 服务名称
- slug
- 描述
- 正文内容
- 图标
- 配图
- 参考时效
- 适合货物
- 排序
- 是否启用

**原则：服务页要有单独表，不要只埋在 JSON 里。**

### 5.3 `news`
适合放：

- 标题
- slug
- summary
- body
- status (draft/published)
- published_at
- seo_title
- seo_description
- seo_keywords
- featured_image
- featured_image_alt
- og_image

**原则：新闻是 SEO 内容引擎，字段一开始就要按内容运营来设计。**

### 5.4 `site_modules`
适合放首页或模块化页面的数据：

- services 模块
- comparison 模块
- faq 模块
- stats 模块
- quote 模块
- footer 模块

这个表最大的好处是：

- 让非技术人员在后台改模块内容
- 便于做多语言内容
- 便于做“页面模块化复制”

### 5.5 `inquiries`
当前项目中，询盘字段逐步扩展后，已经很接近真实业务需要。后续新站建议直接参考这种级别：

- 姓名
- 公司
- 手机
- 邮箱
- 起运地
- 目的地
- 服务类型
- 货物名称
- HS 编码
- 包装类型
- 运输方式（如 FCL/LCL）
- 交付方式（港到港 / 门到门）
- 备注
- 附件
- 多组尺寸重量 package rows
- 汇总 totals
- 状态 status
- 创建时间 / 更新时间

**结论：询盘表单不要只做“姓名+电话+留言”，那种只能收低质量线索。**

## 6. 后台系统怎么做更实用

### 6.1 后台的目标不是“炫”，而是“可运营”
这个项目里后续证明最有价值的后台能力有：

- 服务增删改查
- 新闻编辑与发布
- 媒体库上传/选图/复用
- 首页模块配置
- footer/company settings
- 合作伙伴管理
- 询盘查看与跟进

### 6.2 新闻后台是内容增长核心
这个项目后面重点补强了新闻后台，包含：

- 列表 / 搜索 / 状态筛选 / 分页
- slug 自动生成
- 预览页
- draft / published 状态切换
- autosave
- body 富文本插图
- cover image / og image 选择
- alt 文本建议
- 置顶/推荐控制
- SEO 长度提示

**经验：如果新网站要做 SEO，一定要做一个真正能用的新闻后台，而不是只做个 textarea。**

### 6.3 媒体库要尽早做
这个项目里媒体库后期价值很大：

- 服务图、banner 图、文章图、OG 图都能复用
- 文件分类更清晰
- 减少手工贴 URL
- 提升后台可用性

建议新站一开始就包含：

- 上传
- 分类
- 搜索
- 预览
- 复制 URL
- 在各编辑器里直接选图

## 7. SEO 建设顺序（非常适合复用）

这个项目 SEO 不是一次做完的，而是按优先级分阶段推进。这个顺序非常适合新项目照搬。

### 第一层：全站基础 SEO
先做：

- `title`
- `description`
- `canonical`
- `metadataBase`
- robots
- sitemap
- Open Graph
- Twitter Card

### 第二层：结构化数据
根据页面类型补：

- Organization
- BreadcrumbList
- FAQPage
- Article
- Service
- ItemList

### 第三层：站内内链和锚文本优化
把原来泛泛的按钮文案：

- 立即咨询
- 查看详情
- 先看方案

改成更有搜索意图的：

- 获取中国到欧洲物流方案
- 查看中欧物流服务项目
- 获取中欧物流运输建议
- 查看德国物流方案

**经验：内部链接的锚文本质量会明显影响 SEO 和转化。**

### 第四层：服务详情页 SEO
服务总页远远不够，真正能吃长尾流量的是单独服务页：

- `/services/china-europe-train`
- `/services/truck-express`
- `/services/ocean-freight`
- `/services/eu-customs`
- `/services/door-delivery`
- `/services/project-cargo-transport`

每个服务页建议包含：

- 独立 TDK
- 关键词覆盖
- 服务场景
- 适合客户
- 常见货物
- FAQ
- 服务流程
- 相关服务内链
- 询价 CTA

### 第五层：国家/区域专题页 SEO
后续项目中新增了国家页：

- 德国
- 法国
- 波兰
- 意大利
- 荷兰
- 比利时
- 西班牙
- 匈牙利

这个策略的好处是：

- 更容易吃“国家名 + 行业词”的搜索
- 更容易承接高意图客户
- 可以把服务页和国家页形成网状内链

**结论：服务页吃“方案型”词，国家页吃“地域型”词，文章页吃“问题型/知识型”词。**

## 8. 转化优化顺序（很关键）

这个项目后期不只是做 SEO，也做了明显的转化型改造。

### 8.1 首页 CTA 要具体，不要空泛
不建议：

- 立即咨询
- 联系我们

更建议：

- 获取物流方案
- 获取中国到欧洲物流方案
- 提交中欧物流询价
- 获取一对一方案建议

### 8.2 页面内容要围绕客户决策写
后面被验证有效的内容模块有：

- 适合哪些客户
- 适合哪些货物
- 客户常见顾虑
- 咨询前建议准备
- 典型案例场景
- 常见目的地覆盖
- 服务流程
- FAQ

这些内容比空泛宣传词更接近真实成交过程。

### 8.3 询价模板非常重要
项目后期专门抽了询价资料模板模块。

它的价值：

- 用户知道该提供什么
- 线索质量更高
- 销售跟进更高效
- 减少来回追问

后续新站建议默认配置两套：

- 服务页询价模板
- 国家/专题页询价模板

### 8.4 案例化表达优于抽象宣传
后面做的“案例化场景模块”非常值得复用：

- 场景
- 难点
- 解决思路
- 结果

这种结构天然更适合：

- SEO 长尾词
- 销售说服
- 页面停留时间
- 让客户快速对号入座

## 10. 内容增长系统应该怎么做

### 新闻不是装饰，是 SEO 引擎
这个项目里新闻系统最终的意义不是“发公告”，而是：

- 做长尾词收录
- 强化专业度
- 给首页提供新鲜内容
- 给服务页和国家页提供内链支撑

### 后续新站建议的内容结构
至少准备三类内容：

1. **问题型文章**
   - XX 怎么选

3. **趋势型文章**
   - 行业月度变化

   - 政策/清关提醒

一定要支持：

- 草稿
- 发布
- 预览
- 图片管理
- SEO 字段
- 置顶/推荐
- autosave

否则后续内容生产会很痛苦。

## 11. 生产部署与环境管理经验

### 11.1 一定要确认“本地目录 / Git / Vercel 项目”映射
这是这个项目最重要的流程教训之一。

新站启动前，必须记录：

- 本地目录名
- Git 仓库地址
- Vercel project 名称
- 正式域名
- 预览域名

### 11.2 本地提交不等于线上已更新
项目中出现过一次关键问题：

- 改动只在本地 commit
- 用户去 GitHub 看 remote commit，发现没更新
- 结果以为“你明明做了但线上没变”

**结论：每次上线要明确完成这几步：**

1. `git add`
2. `git commit`
3. `git push`
4. `vercel deploy --prod --yes` 或确认自动部署
5. 确认正式域名 alias 生效

### 11.3 构建前先本地 build
这个项目中，多次先本地 `npm run build` 才发现：

- 类型错误
- Supabase 初始化时机错误
- 某些 API route 在 build 时就触发环境依赖

**经验：任何生产部署前，都先本地 build。**

## 12. 技术踩坑与解决办法

### 坑 1：Supabase client 在 import 时就初始化，导致 build 失败
曾出现的问题：

- auth/admin API route 在 import 阶段就读取环境变量
- Next build 时触发失败

解决：

- 改成 **lazy runtime initialization**
- 不要在 module 顶层直接 create client

**新站规范：所有依赖环境变量的 client 尽量放进函数里延迟初始化。**

### 坑 2：admin/login 被 admin layout auth guard 包裹，导致空白页
解决：

- 登录页不能被同一层未登录保护逻辑拦截
- 登录页应在 auth guard 外，或 guard 要显式放行 login route

### 坑 3：footer 配置写进 site_config 但前台没接线
解决：

- site_config 改完，不代表前台会自动显示
- 所有页面都要真正把配置 props 传给 Footer

**新站规范：全站公共组件的配置项要逐页检查接线是否完整。**

### 坑 4：新闻 autosave 把已发布文章写回 draft
根因：

- autosave 固定 POST `status: draft`

解决：

- autosave 必须保留已有状态和 published_at
- local draft restore 不能覆盖真实 published 数据

**新站规范：草稿与发布状态一定要分清，autosave 不能破坏正式内容。**

### 坑 5：媒体库把文件夹当图片
解决：

- API 递归时要过滤真实文件
- 目录项不能直接当媒体项展示

### 坑 6：相似项目目录混淆
解决：

- 开始工作前先核对 `.vercel/project.json`
- 核对 remote origin
- 核对线上正式域名

## 17. 最终结论

这个项目最宝贵的，不只是做出了一个物流网站，而是跑通了一套**企业官网 + 内容增长 + 询盘转化 + 后台运营 + SEO 扩展**的方法论。

后续做新网站时，最应该复制的是这些原则：

1. **先确认项目映射，别改错站**
2. **从一开始就按“可运营系统”设计，不要只做展示页**
3. **服务页、专题页、文章页要一起布局，别只做首页**
4. **询盘表单要做深，别只收一句留言**
5. **SEO、转化、后台能力必须同步推进**
6. **每次上线前先 build，再 push，再 deploy，再核验正式域名**
7. **案例化内容、询价模板、FAQ、顾虑模块，都是提高成交的关键**

如果后续要做新行业网站，这份文档可以直接当第一版项目蓝图使用。
